# ADR: AI data boundary

## TL;DR

Two zones. **EU zone** (prod API, PostgreSQL, OVH object storage, Alexandra Instituttet LLM, Scaleway Whisper) may see personal data. **Public zone** (GitHub repo/PRs/Actions, Claude via subscription) may not — ever. The only thing that crosses EU → public is a technical **fix spec**, generated by the EU LLM and passed through a deterministic PII guard; it must be publishable because it becomes the PR body. Code-changing agents run only in GitHub Actions. AI never writes migrations and cannot merge to `main` (auto-merge cap is 0 until trusted).

## Status

**Accepted**

## Context

The feedback/bug-report feature ([task 45](../../tasks/feedback/45-feedback-capture.md)–[47](../../tasks/feedback/47-feedback-ai-fix-prs.md)) sends user reports — screenshots, descriptions, recent actions — to AI for triage and, for trivial bugs, an automatic code fix. Those reports contain children's names, absence reasons and kontaktbog content.

Constraints:

- The repo is **public** by choice (open source + marketing). Issues, PR bodies and Actions logs are world-readable. GitHub-hosted runners are not EU-guaranteed.
- EU residency is already the stance for every vendor ([tech-stack](tech-stack.md), [transactional-email](transactional-email.md)). Friskole boards are sensitive to non-EU processing of children's data. The owner prefers EU even at the cost of a worse developer experience.
- Pre-revenue: the whole system must run at essentially €0 infra (< $5/month). No extra VPS.
- Running an agent that reads untrusted user text on the prod VPS (next to PostgreSQL and Keycloak) was rejected as a security risk.
- Claude Code in GitHub Actions on the Pro/Max subscription is already proven by `nightly-improvement.yml` and costs nothing extra.

## Decision

1. **Personal data never leaves the EU zone.** Raw reports, screenshots, user text and names are stored in our PostgreSQL / OVH and shown only in the SuperAdmin backoffice.
2. **Data minimisation inside the EU zone too.** The EU LLM receives the *masked* screenshot / DOM outline and *redacted* text (known tenant names, CPR, phone, email replaced), not the raw copy.
3. **Triage runs in the API** as a single HTTP call to Alexandra Instituttet (Danish-hosted, OpenAI-compatible). No code execution, no repo checkout — source files are fetched from the public repo at the deployed sha.
4. **The only EU → public crossing is the fix spec**: a technical description (route, viewport, observed, expected, likely files). It passes a deterministic PII guard (tenant name list, CPR/phone/email regex, no long verbatim overlap with the user's text). Failing the guard means it stays in the EU zone for human review.
5. **Code-changing agents run only in GitHub Actions** on the public repo (free minutes, Claude via `CLAUDE_CODE_OAUTH_TOKEN`), triggered by `repository_dispatch` with the spec. Never on the prod VPS.
6. **AI never writes migrations** and never touches `.github/`, `infrastructure/`, `api/**`, dependencies or auth code — enforced by a CI guard, not by the prompt.
7. **AI cannot merge to `main`.** Auto-merge is built but capped by repo variable `AI_AUTOMERGE_MAX_FILES=0`.

## Consequences

### Positive

- **POS-001**: No new sub-processor outside the EU for personal data; the story to a friskole board is simple.
- **POS-002**: Claude quality where it matters (writing code) without Claude ever seeing personal data.
- **POS-003**: €0 infra — triage is one outbound HTTP call from the existing API; agents use free public-repo Actions minutes and the existing subscription.
- **POS-004**: Prompt injection via a user report can at worst produce a bad PR that CI, the guard and a human reviewer see before merge.

### Negative

- **NEG-001**: Triage quality is bounded by the Alexandra model, which is weaker than Claude; misclassification sends reports to `needs-human` (safe, but more manual work).
- **NEG-002**: The fix agent only sees the spec, not the screenshot — layout bugs must be described well enough in text.
- **NEG-003**: Subscription rate limits are shared with interactive use; fix runs are throttled (one at a time, daily cap).
- **NEG-004**: The PII guard is planned ([task 47](../../tasks/feedback/47-feedback-ai-fix-prs.md) `FixSpecGuard`) and **not yet enforced**; until that dispatch gate exists, fix specs must stay in the EU zone. Once built it is heuristic: a spec could in theory carry a unique non-name identifier ("the girl with diabetes"). Mitigated by the spec format being technical and the guard's verbatim-overlap check.

## Alternatives Considered

### Private feedback repo + Claude for triage

- **ALT-001**: **Description**: Reports as issues in a private GitHub repo; Claude Code Action triages there.
- **ALT-002**: **Rejection Reason**: Puts personal data at GitHub and Anthropic (US). Rejected once EU residency was made a hard preference.

### Claude via AWS Bedrock (Frankfurt)

- **ALT-003**: **Description**: Same Claude quality, EU-region processing.
- **ALT-004**: **Rejection Reason**: US company (CLOUD Act), pay-per-token, and not EU-owned. Kept possible: the LLM client is OpenAI-compatible and model-agnostic.

### Dedicated worker VPS / agent on the prod VPS

- **ALT-005**: **Description**: A container running an agent harness against an EU model, on its own VPS or co-located with prod.
- **ALT-006**: **Rejection Reason**: Separate VPS costs money pre-revenue; co-location exposes the prod host to an agent processing untrusted text.

### Self-hosted open model on a GPU

- **ALT-007**: **Description**: Run Devstral/Qwen-coder/GLM ourselves.
- **ALT-008**: **Rejection Reason**: GPU cost and maintenance.

## Implementation Notes

- **IMP-001**: One shared `ILlmClient` (OpenAI NuGet, configurable base URL/model) — built for feedback triage, reused by [task 21](../../tasks/21-ai-suggestions-for-schema.md).
- **IMP-002**: Per-tenant opt-out `AllowAiFeedbackProcessing` (default on). Off → no LLM call, no dispatch; report still reaches the backoffice.
- **IMP-003**: Alexandra Instituttet and Scaleway (transcription) go on the sub-processor list — see [task 48](../../tasks/48-databehandleraftale.md). GitHub and Anthropic do not, because they never receive personal data.
- **IMP-004**: Any future AI feature must place itself in one of the two zones. A feature that needs personal data *and* code execution is not allowed under this ADR without superseding it.
