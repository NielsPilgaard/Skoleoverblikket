# AGENTS.md

How AI agents work in this codebase.

## Product

Skoleoverblikket is affordable, dead-simple admin software for Danish schools: multi-tenant SaaS, one tenant per school, Danish-language only. The schema planner (weekly class schedules with real-time conflict detection) is the core, but the product is the school's full admin backbone: SFO, ugeplan, vikardækning, parent communication, fravær, ferieindmelding, files, bestyrelse and stå-mål-med. The goal is less money and time spent on admin and fewer disconnected tools. Feature → controller map: [docs/FEATURES.md](docs/FEATURES.md).

- **Market**: primarily friskoler and private schools; secondarily folkeskoler, which pick their timetable tool independently (Aula is a separate communication product). Typical customer: a friskole in a small town, ~300 students, 25 staff.
- **Simplicity is the core value.** Every UI decision must pass: can Hanne, the 58-year-old school secretary, do this without training or asking for help? Prefer fewer options, and obvious over clever. See [docs/PERSONAS.md](docs/PERSONAS.md).
- **Responsive**: the schema builder (admin) is laptop-first. Staff schedule views must work fully on a phone. No feature may be unusable at any screen size.
- **Billing**: self-serve Stripe Checkout only. 30-day free trial, then monthly. No manual invoicing, no MobilePay.
- Before assuming a design choice is arbitrary, check the ADRs: [docs/adr/INDEX.md](docs/adr/INDEX.md).

## API (ASP.NET Core / C#)

**Multi-tenancy**: every query on tenant data is scoped by the EF Core global query filter `HasQueryFilter(e => e.TenantId == _tenantContext.TenantId)`. Never bypass it. TenantId comes from `ITenantContext`, never as a method parameter through business logic. Never trust a URL slug as authorization; resolve it to a TenantId at the middleware boundary. `IgnoreQueryFilters()` needs a comment explaining why and a tenant-isolation test. Never hard-code school names, branding or other tenant-specific values.

- REST, versioned at `/api/v1/`. The OpenAPI spec is generated by Swashbuckle; never hand-write it.
- All errors are `ProblemDetails` (RFC 7807). No plain strings or custom error shapes.
- Every endpoint requires a Keycloak JWT unless explicitly marked anonymous. Never allow anonymous access to tenant data.
- Role and ClassPermission logic (admin vs. staff, superadmin vs. restricted class editing) is non-obvious. Read [docs/AUTHORIZATION.md](docs/AUTHORIZATION.md) before touching auth.
- Never modify an existing EF Core migration. Generate a new one with `/add-migration`.

### Encapsulation: thin controllers, feature services

Most breakage here comes from controllers that load an entity, set its fields and call `SaveChangesAsync`. When several controllers and test helpers change the same entity, each with its own idea of a valid state, a new required field or rule breaks all of them at once. The fix: **controllers handle HTTP, one plain service per feature handles data and rules.** This is not DDD. EF Core already is the repository and unit of work.

**Controllers** bind the request, authorize via attributes (`[Authorize(Roles = ...)]`, `EditClassRequirement`, `ParentClassAccessRequirement`), call one service method, and map the result to `Ok`, `NoContent`, `CreatedAtAction` or `ProblemDetails`. They never inject `AppDbContext`, call `SaveChangesAsync`, trigger side effects, or branch on business state (open/closed, expired, already accepted, conflicts).

```csharp
[HttpPut("{id:guid}")]
[Authorize(Roles = Roles.Admin)]
public async Task<IActionResult> UpdateWindow(Guid id, UpdateWindowRequest req, CancellationToken ct) =>
	await vacationRegistrations.UpdateWindowAsync(id, req, ct) ? NoContent() : NotFound();
```

**Services** live in `api/Skoleoverblikket.Api/Services/`, are registered in `AddDomainServices`, and follow `ClassMembershipService` and `StaffInvitationService`:

- One `sealed` concrete class per feature (`VacationRegistrationService`), with a primary constructor taking `AppDbContext`, `ITenantContext` and whatever else it needs. Inject it as the concrete type.
- The owning service is the only writer of its entities. Other features call its methods. Reading another feature's tables with a projection is fine.
- `new Entity { ... }` appears only in the owner's create method, in production code and tests alike. That method sets `TenantId` and defaults.
- Give a rule or side effect its own named method (`OpenWindowAsync` sends notifications). A plain edit with no rules is fine as `UpdateWindowAsync(id, request)`.
- A method loads, checks, changes, saves once, then triggers side effects (notifications, email).
- No HTTP: no `IActionResult`, `ProblemDetails`, status codes or `HttpContext`. The controller passes in what is needed, such as `User.GetKeycloakSubject()`.
- Return DTOs from `AsNoTracking` + `.Select(...)` projections. Request and response records live next to the service, and the controller uses them directly. No command objects, no mapping layer.
- Failures: return `null`/`bool` for a single failure case, or a small enum when the controller must tell apart several (not found, not your child, window closed). Throw only for bugs and infrastructure failures.
- Data-level authorization ("does this parent own this student?") lives in the service. Role and policy checks stay on the controller.

**Don't introduce** these, and push back if a task seems to need one: repositories or wrappers around `AppDbContext`; an interface per service (only for a real second implementation or an external system tests replace, like `INotificationService`, `IEmailSender`); CQRS, MediatR or handler-per-operation; aggregates, value objects, domain events or behavior on entities; AutoMapper; generic base services/controllers or Application/Domain/Infrastructure projects; splitting a service before ~500 lines (then split by sub-feature, not layer). A new abstraction must remove real duplication or protect a rule that exists today.

**Legacy controllers** that write to `AppDbContext` directly still exist. Don't big-bang refactor them.

- New endpoint or feature: follow this section.
- Changing an existing endpoint's logic: move that logic into the feature's service in the same PR, creating the service if needed.
- Unrelated small fix (typo, status code, attribute): no extraction needed.
- Entity creation moved into a service: switch `TestDataBuilder` and hand-built tests to it in the same PR.

Before finishing API work, check that no controller you touched still writes to `AppDbContext` for the entity you changed.

## Frontend (React / TypeScript)

- Call the API only through the generated client (hey-api/openapi-ts), regenerated with `/codegen`. Never read, grep or diff `web/src/api/generated/` or `openapi/` (their lines are 12k+ characters). Find hook names from usages in `web/src/pages`.
- Tailwind utility classes only. No CSS-in-JS, inline `style` props or component `.css` files.
- Function components with hooks only.
- Landing page cards come from `web/src/content/features.tsx`. Every sidebar route must be mapped in `sidebarRouteFeatures` (to a feature or `null`), or `tsc` fails. A new user-facing feature adds or updates its card in the same PR.
- `feat:` commit subjects feed the weekly `/nyheder` changelog draft (`.github/workflows/changelog.yml`), so describe what the user gets.

## Naming

Code identifiers are English, except these kept Danish domain words: klasse, lokale, lektion, lærer, pædagog, skema, SFO ([docs/GLOSSARY.md](docs/GLOSSARY.md)). UI text and user-facing web URLs are Danish. API route paths are English.

## Testing

Strategy: [docs/TESTING.md](docs/TESTING.md).

- Two layers only: API integration tests (tUnit + WebApplicationFactory + Testcontainers) and Playwright e2e for critical flows.
- Never mock `DbContext` or `ITenantContext`. Use real PostgreSQL via Testcontainers, because mocks bypass the query filter.
- Test only through public HTTP endpoints or rendered UI, never private methods.
- Playwright selectors use `data-testid` only.
- One test file per feature flow, not per class.
- Data the API can't create: `TestDataBuilder` resolves the owning service from `factory.Services` and calls its create method, never `db.Add(new Entity { ... })`.
- Does it need a test? Yes, if a silent break would block Hanne.

## Before declaring done

Both must pass:

1. `/verify`: Biome, TypeScript build, dotnet format (auto-fixes), dotnet build, API integration tests (needs Docker), ryni (Markdown links + `SKILL.md` metadata; install with `scripts/setup.ps1`).
2. `/test`: Playwright e2e (`cd web && npx playwright test --reporter=line`; starts Aspire, or pass `SKIP_ASPIRE=1` if it's already running).

Other skills: `/add-migration`, `/codegen`, `/ci-failure` (diagnose a red CI, PR e2e, Staging or deploy run).

A pre-commit hook (`.githooks/`, enabled by `npm install` in `web/`) formats staged files, so formatting never fails CI. Biome lint and TypeScript errors do. On PRs, `ci-fix.yml` lets Claude try one fix. `main` is branch-protected.

### Cloud sessions

With `CLAUDE_CODE_REMOTE=true` there is no Docker, so the steps above don't apply. `scripts/cloud-setup.sh` installs the .NET SDK and web dependencies.

1. Run `npm --prefix web run lint`, `npm --prefix web run build`, `dotnet build api/Skoleoverblikket.Api/Skoleoverblikket.Api.csproj` and `dotnet format api/Skoleoverblikket.Api/Skoleoverblikket.Api.csproj`.
2. Commit to a branch and open a PR. Never push to `main`. PR CI runs integration tests and e2e.
3. In the PR description, list the checks you ran and say integration tests and e2e were left to CI. Never claim tests passed that you didn't run.
4. Changes in `api/Skoleoverblikket.Api/Data/Migrations/` fail the `Migration review` check until the owner sets the `migration-reviewed` label. Never set it yourself.
5. No Grafana access: diagnose prod issues from the error text or stack trace the user pastes.
